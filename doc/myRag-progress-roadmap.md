> 文档定位：开发进度基线、阶段验收清单、后续路线图

## 1. 项目目标与定位

**目标：** 从已跑通的 Spring AI + Qdrant + Qwen RAG
原型，逐步建设为具备**知识库管理、文档入库、可扩展检索、效果评测、异步任务与可观测性**的
Java RAG 框架。

最终希望支持：创建多个知识库、上传真实文档、解析与切片、索引和重建、按知识库隔离检索、生成带来源的回答；再逐步加入
BM25、RRF、Rerank 和工程化能力。

**原则：**
先做可用知识库，再做算法增强；每个阶段有可运行接口、测试与明确验收标准；不要把"计划中的功能"写成"已经上线"。

### 当前系统已跑通的数据流

``` text
手工输入知识 → Embedding(text-embedding-v4) → Qdrant
用户问题 → Embedding → Qdrant TopK + 相似度过滤
         → 拼装 Context / Prompt → Qwen(qwen-plus)
         → 回答 + sources
```

**当前最大短板：**
真实知识的批量入库、维护与隔离能力不足；这比继续增加检索算法更影响项目可用性。

## 3. 已完成阶段的技术收获

1.  **模型职责区分：** Embedding 负责语义表示，Chat 模型负责生成回答。
2.  **向量检索：** Qdrant 使用固定维度向量及相似度搜索，TopK
    不等于"必然相关"。
3.  **RAG 闭环：** 检索结果必须显式传入 Prompt，大模型不会自动读取
    Qdrant。
4.  **低相关性与幻觉：** 曾出现"问销售目标却返回 Redisson
    内容"；需要阈值、空结果处理、Prompt 约束和后续评测。
5.  **工程排障：** 解决模型兼容 API 路径问题；通过 SSH 隧道连接云端
    Qdrant。
6.  **源码管理：** 项目已推送个人 GitHub；继续做好 API
    Key、私钥及敏感资料检查。

> 质量提醒：此前模型生成的 `tryLock(10, 30, TimeUnit.SECONDS)`
> 示例将"显式租约"与"看门狗续期"混淆，说明有来源不代表答案事实正确；后续需要答案忠实性与引用评测。

## 5. 下一阶段：知识库 MVP（优先执行）

### 5.1 为什么要先做知识库

现在的知识多靠手工 `new Document(...)`
添加，难以支撑真实使用和检索评测。下一阶段应让系统从"能问一句话"变为"能维护一批真实文档"。

### 5.2 MVP 范围与优先级

-   **P0：** 创建/列表/详情知识库；TXT/MD
    文件上传与原文件存储；解析、文本清洗、Chunking；Embedding 和 Qdrant
    索引；文档状态；按知识库过滤检索；回答返回文件/Chunk
    来源；删除文档及索引。
-   **P1：** PDF/Word；SHA-256 去重；重新索引、失败重试、文档版本；简易
    Web 管理界面。
-   **暂不做：** 复杂
    RBAC、多租户计费、工作流编排、分布式调度和大规模性能优化。

### 5.3 推荐数据模型

-   `rag_knowledge_base`：知识库 ID、名称、描述、状态、创建/更新时间。
-   `rag_document`：文档 ID、知识库
    ID、文件名/类型/路径、哈希、处理状态、Chunk 数、错误信息、时间。
-   `rag_document_chunk`：文档 ID、Chunk 顺序、向量
    ID、内容哈希、来源页码/位置（可选）。
-   **文件存储：** MVP 用本地目录，后续抽象为
    OSS；不要只保留上传时的临时文件。
-   **向量存储：** 当前先沿用共享 Qdrant Collection，在 Payload 中写入
    `knowledgeBaseId`、`documentId`、`chunkIndex`、`sourceName`
    等字段，并对检索应用服务端过滤。必要时创建 Payload 索引。

> MySQL 和 Qdrant 没有天然跨库事务。先以
> `PENDING → PROCESSING → COMPLETED / FAILED`
> 管理状态，并为删除、重建和异常恢复设计幂等/补偿策略。

### 5.4 API 规划

``` http
POST   /api/knowledge-bases
GET    /api/knowledge-bases
GET    /api/knowledge-bases/{id}
DELETE /api/knowledge-bases/{id}

POST   /api/knowledge-bases/{id}/documents
GET    /api/knowledge-bases/{id}/documents
DELETE /api/knowledge-bases/{id}/documents/{documentId}

POST   /api/knowledge-bases/{id}/chat
```

建议让知识库 ID
由后端根据实际授权和资源关系验证；将来接入多租户时，不能只相信客户端提交的
ID。

### 5.5 按实施顺序拆解任务

-   [ ] **任务 0：确认 Retriever SPI 是否已合入并回归通过。**
    如果未完成，先让 `RagService` 依赖 `Retriever`
    接口，保留现有阈值行为。
-   [ ] **任务 1：建立 MySQL 表及知识库 CRUD。**
    验证创建、查询、删除的业务状态与异常处理。
-   [ ] **任务 2：实现 TXT/MD 上传与本地文件存储。**
    验证文件大小、格式、文件名安全及重复上传策略。
-   [ ] **任务 3：实现 `DocumentParser` 与 `TextChunker` 接口。**
    先用固定长度 + Overlap 基线，再考虑段落/Token
    感知切分；测试边界条件。
-   [ ] **任务 4：实现入库 Pipeline。**
    `文件 → 解析 → Chunk → Embedding → Qdrant`，保存元数据与处理状态。
-   [ ] **任务 5：改造检索和问答。** `RetrievalQuery` 带
    `knowledgeBaseId`；检索时使用 Payload Filter；回答返回文件名/Chunk
    ID。
-   [ ] **任务 6：实现文档删除与一致性处理。**
    删除文档后不应继续检索到它；失败要可观察、可重试。
-   [ ] **任务 7：准备真实技术资料并端到端验收。** 使用允许导入的
    Java/Spring/Redis/MySQL 文档，至少覆盖两个知识库。

### 5.6 MVP 验收场景

1.  创建 `Java 技术知识库` 与 `数据库知识库` 两个知识库。
2.  分别上传至少 3 份 TXT/MD 文档；查看处理状态和 Chunk 数量。
3.  针对 Java 库提问 Redisson 问题：能回答并返回来源文档。
4.  针对数据库库提问相同问题：不能召回 Java 库中的 Redisson 内容。
5.  提问资料之外的"公司明年销售目标"：应拒答或明确资料不足。
6.  删除某文档并再次提问：该文档的 Chunk 不再出现在检索结果中。
7.  模拟 Embedding 调用失败：文档状态标记 `FAILED`，不假装索引成功。

## 6. 知识库之后的检索增强路线

### 6.1 Retriever SPI（如尚未完成，提前补齐）

``` text
RagService → Retriever 接口
                 ├─ QdrantDenseRetriever
                 ├─ LuceneBm25Retriever
                 └─ HybridRetriever / RetrievalRouter
```

统一 `RetrievalQuery` 和
`RetrievedChunk`；未来支持知识库过滤、检索模式和元数据。多实现时通过
Router/编排器明确选择，避免注入歧义。

### 6.2 BM25 与 RRF

-   引入 Lucene BM25
    和中文分词，弥补向量检索对错误码、精确类名、配置项、SKU
    等术语的不足。
-   用 RRF 融合 Dense 与 BM25
    排名；先用可解释的默认参数作为基线，再实验调参。
-   不同检索器的原始 `score` 不应直接视为可比较数值。

### 6.3 Rerank 与评测

-   对融合后的候选 Chunk 重排序，再送入 LLM。
-   构建人工标注问答集（先 30--50 条，逐步扩展到 100--500 条）。
-   记录 Recall@K、MRR、nDCG、拒答准确性、引用忠实性、P50/P95
    延迟和调用成本。
-   每次优化都保留基线结果，避免"功能越多，效果却没有变好"。
